# 适用场景
当一个主题已经不再是“纯基础知识”，而是开始进入：
- 设计目标
- 工程取舍
- 底层机制
- 边界与例外

这时不要再把内容写成：

概念 → 定义 → 对照表

而要重构成：

真实问题 → 设计目标 → 取舍方案 → 底层机制 → 边界与例外

也就是说：先让读者产生问题，再给答案，再继续追问。

# 任务目标
给定一个已有 STACK（以及它挂载的 CARDS），把它重构成“问题驱动”的阅读路径，让读者愿意顺着往下读，而不是只在背知识点。

## 允许做的事
1) 重排目标 STACK 的章节顺序
2) 调整部分 CARD 的标题，让标题更像“问题”
3) 轻量改写 CARD 的 Point / Why / Example，使其更像“回答问题”
4) 必要时新增少量“引导式问答页”到 `QA/`
5) 更新 STACK 中的目录区与 `Read (embed)` 顺序

## 不要做的事
1) 不要新开知识主线
2) 不要大规模重写所有 CARD 内容
3) 不要随意改文件名；能保留原文件名就保留
4) 不要把问题驱动写成大段散文
5) 不要把 REVIEW 当成主线引导页来改

# 核心设计原则
## 1) 问题优先，不是术语优先
优先把读者会问的问题排在前面，例如：
- 为什么默认不是 RC？
- 为什么不是直接上 Serializable？
- 为什么普通 `SELECT` 不想总加锁？
- 为什么同样是两次查询，RC 会变而 RR 更稳定？

不要一开始就堆：
- MVCC 是什么
- Read View 是什么
- Repeatable Read 是什么

这些术语应该在问题的牵引下出现。

## 2) 标题改成“问题式”优先
如果某张卡原本是术语标题，允许改成问题式标题，但尽量不改文件名。

例如：
- `tx__what_is_mvcc.md`
  标题可改为：`为什么普通 SELECT 不想总等锁？MVCC 怎么帮忙？`
- `tx__what_is_read_view.md`
  标题可改为：`数据库怎么知道你这次该看哪个版本？`
- `tx__snapshot_read_vs_current_read.md`
  标题可改为：`什么时候读快照，什么时候必须读最新值？`
- `tx__rc_vs_rr_read_view_timing.md`
  标题可改为：`为什么 RC 两次 SELECT 会变，而 RR 更稳定？`

## 3) 引导式问题不要放到 CARDS，应放到 QA
如果需要在 STACK 里先抛问题，可以新增少量“引导式问答页”到 `QA/`。

规则：
- `QA/` 里的文件不是原子 CARD
- 文件名建议：`<topic>__<question_slug>.md`
- 内容应以“Point + Why + 直接展开的阅读路径”为主
- `QA` 允许一页串多张 `CARD`
- `QA` 不要替代 REVIEW；它是读前引导，不是复习题
- 只保留高价值问题，不要写教学过渡语或凑数问题

## 4) Questions / Scenarios 的位置
如果使用引导式问答页：
- `QA` 要在 STACK 中直接 `![[...]]` 展开
- 不要只放成一排链接让用户点进去
- `Q&A / Start Here` 小节应放在：
  - 目录区之后
  - `Read (embed)` 之前
- 不要放在整页最顶端

# 推荐结构
默认把目标 STACK 重构成下面 5 段；若主题不同，可微调名称，但结构逻辑尽量保持一致：

1. `Q&A / Start Here`
2. `Core Model`
3. `Phenomena`
4. `Isolation Levels / Mechanism`
5. `Design / Tradeoff`

对应阅读体验：
1) 先带着问题
2) 再补最小模型
3) 再看现象
4) 再看不同方案怎么处理
5) 最后回到设计权衡与总结

# CARD 改写要求
对已有 CARD 的改写只做“最小必要重构”：
- 优先改 H1 标题
- 再改 Point / Why 的句式
- 保持内容短
- 保持 `Refs`
- 不要随意追加很多 related

推荐写法：
- `Point`：一句话回答标题中的问题
- `Why`：讲清为什么值得这样设计 / 为什么不能简单用别的方法
- `Example`：给一个最小场景

# STACK 改写要求
1) 保留现有 stack 文件路径
2) 调整 Cards 目录顺序，使其符合问题驱动阅读路径
3) 如果使用 `QA`：
   - 在 `Q&A / Start Here` 中直接 `![[QA/...]]` 展开
   - 然后再进入 `Read (embed)`
4) `Read (embed)` 仍以正文 CARD 为主，不要把 `QA` 混到正文连续阅读里
5) 不要让同一张正文卡在 `Read (embed)` 里重复出现

# 输出要求
默认直接在仓库里修改文件：
- 更新目标 STACK
- 更新必要的 CARDS
 - 如有需要，新增少量 QA 页到 `QA/`

不要输出完整文件内容。

最后只给一个简短变更摘要：
1) 修改了哪些文件
2) 新增了哪些 QA 页
3) STACK 是否已按“问题驱动”顺序重构完成

# 适合优先使用本 prompt 的主题
- 事务 / MVCC / Locks
- 索引设计与索引失效
- 一条 SELECT 的执行流程
- 锁、日志、执行计划这类“机制 + 取舍”主题

# 不适合优先使用本 prompt 的主题
- 纯 SQL 语法基础
- 纯模板整理
- 纯 sources 导航页
