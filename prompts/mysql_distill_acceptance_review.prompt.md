# MySQL Distill 验收标准

用于验收 MySQL 蒸馏产物，尤其是子线程生成的 `CARD`、`STACK`、`QA`、`REVIEW`。验收时先按本文件逐条检查，再决定是否接收。

## 1. 资料边界

- 只能使用本仓库资料：`sources/`、现有 `CARDS/`、`STACKS/`、`QA/`、`REVIEW/`。
- 冲突时优先级：`sources/refman-*` > `sources/JavaGuide-mysql/` > 其他本地资料。
- 本地资料无法确认的结论，写具体 `TODO`，不要补成确定语气。

## 2. 主线边界

- 当前 stack 只回答自己的问题，不顺手展开别的主线。
- 基础页先建立模型，再进入追问；不要一上来放高阶 QA。
- 机制页可以问题驱动，但问题必须服务主线，不要凑数。
- 不要把优化器、锁、统计信息、日志、事务等旁支塞进索引基础或 B+Tree 查询路径。

## 3. CARD 验收

每张卡必须只讲一个点。

- `Point`：直接回答“这一步是什么 / 这个结构是什么 / 这个规则是什么”。
- `Why`：必须回答“为什么需要它 / 为什么这样设计 / 它解决什么真实问题”。
- 禁止空 `Why`：
  - 不写“为了后续理解”
  - 不写“帮助学习”
  - 不写“明确概念”
  - 不写“这题本质在问”
  - 不写教学腔过渡句
- 术语必须先有功能上下文，再落字段名或规则名。
- `Point`、`Why`、`SQL/Notes`、`Refs` 之间必须留空行。
- `Refs` 必须指向本地路径或本地资料定位。

## 4. STACK 验收

- `Cards` 和 `Read (embed)` 顺序必须一致。
- `Read (embed)` 必须能一页顺序读完。
- 阅读顺序必须体现因果链：
  - 先问题 / 动机
  - 再最小模型
  - 再机制步骤
  - 再效果 / 代价 / 边界
- 不要把 stack 写成长文章。
- 不要在 stack 里堆 `Refs`。

## 5. QA 验收

- QA 只回答一个高价值问题。
- QA 用来串联已有 CARD，不替代 CARD。
- `Point` 不写“这题本质在问”，直接说问题核心。
- `Read Through` 优先嵌入 2 到 4 张最相关 CARD。
- QA 放置位置必须匹配读者前置知识；基础模型没建立前，不要提前放 QA。

## 6. REVIEW 验收

- 一题只绑定一张 CARD。
- 答案短，只做唤醒，不写成长解释。
- `See: [[CARDS/xxx]]` 必须在 `</details>` 外，且不带 `.md`。
- 删除重复题、凑数题、只考术语不考理解的题。

## 7. 最后检查

提交前必须检查：

- 是否存在断链或旧文件名残留。
- 是否把超纲内容放进当前主线。
- 是否有乱码。
- 是否误改 `.obsidian/workspace.json`。
- 是否有不相关文件混入本次改动。
